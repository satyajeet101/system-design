## Angular

- Walk me through the architecture of an Angular app you led — module structure, lazy loading, shared/core modules.
  - **Module structure:-** I organized it around Angular's core/shared/feature pattern.
  - **Core module:-** singleton, app-wide stuff loaded once: auth interceptor, error interceptor, the auth guard, app-level services like the current-user/session service. Imported once in AppModule and guarded against re-import.
  - **Shared module —** reusable, stateless building blocks: common UI components (buttons, modals, file-upload widget, data tables), pipes, and directives used across multiple features. No business logic lives here — just presentation.
  - **Feature modules —** one per business capability, each lazy-loaded on its own route: an OffersModule for creating/managing offers, a RewardsModule for reward management, and a BulkRegistrationModule for the file-upload/bulk-registration flow. Each feature module owns its own components, services, and routing.

  - **Lazy loading:-** Each feature module is lazy-loaded via loadChildren in the routing config, so a rep landing on the Offers screen doesn't pay the bundle cost for Bulk Registration or Rewards until they navigate there. That kept our initial bundle small and load times fast, which mattered because reps are often on the app throughout the day and first-load speed affected adoption.

  - **Bulk registration flow specifically:-** That module has a file-upload component (using the shared upload widget) that pushes the file to S3 — either via a presigned URL fetched from our backend, or through a direct-to-S3 upload API. Once the file lands in S3, an S3 event triggers a Lambda that parses the file and calls our registration API to process each record. On the Angular side, since that processing is async, we polled a status endpoint (or used a notification/status service) to show the rep upload progress and success/failure results, rather than blocking the UI waiting on a synchronous response.

  - **Cross-cutting concerns-** Auth guards protect routes based on rep roles/permissions, an HTTP interceptor attaches the auth token and handles token refresh, and a global error interceptor standardizes how API errors surface to the UI so every feature module doesn't reimplement error handling."

  - **Bulk regestration**
    - Since the bulk registration flow is asynchronous by nature — file lands in S3, Lambda picks it up, calls the registration API per record, and that can take anywhere from seconds to a couple minutes depending on file size — I couldn't just wait on a synchronous HTTP response in Angular.

    - What I did: after the upload to S3 succeeds, the Angular app gets back a batch/job ID (either from the presigned-URL API or a follow-up call), and then polls a status endpoint at a set interval — say every few seconds — to check progress: queued, processing, completed, with a count of success/failure records. I showed that as a progress indicator in the UI so the rep isn't left staring at a spinner with no feedback, and once it completes, I surfaced a summary — how many records succeeded, and a downloadable/viewable list of failures with reasons, since bulk uploads often have some rows that fail validation.

    - I chose polling over WebSockets deliberately — this wasn't a high-frequency, low-latency requirement, and reps aren't watching the screen character-by-character; a few-second polling interval was perfectly acceptable UX and much simpler to build and operate than standing up a WebSocket/pub-sub channel just for this one flow. If I were building a feature where near-real-time updates truly mattered — like a live dashboard many reps watch simultaneously — I'd lean toward WebSockets or server-sent events instead, but here it would have been over-engineering.

    - One thing I made sure to handle: if a rep navigates away and comes back, or refreshes, the status polling should resume based on the job ID rather than losing track of an in-flight upload — so I persisted the job ID (e.g., in a query param or a lightweight local state) rather than only holding it in component memory."

- How do you manage state in Angular — services with RxJS Subjects, NgRx, or something else? When would you introduce NgRx vs. plain services?
  - Offers and Rewards are related — a reward is often attached to an offer — so there's a natural question of how those two feature modules share state without becoming tightly coupled.

  - I avoided reaching for NgRx by default here. The interactions were fairly contained — mainly 'when creating/editing an offer, let the rep attach or look up an existing reward' — so I used a shared, injectable service (provided in root, or in a shared module) that exposes the cross-cutting data both features need, like a lookup of available rewards, via RxJS BehaviorSubject/observables. Each module subscribes to what it needs rather than modules importing each other directly or passing data through routes.

  - **Where I drew the line for NgRx:** if the app had gotten to the point where offer state, reward state, and bulk-registration status all needed to interact in complex ways with many components reading and writing the same state — especially with things like undo, time-travel debugging, or many simultaneous async updates — that's when I'd introduce NgRx. For this app, the interaction was narrow enough that a shared service with RxJS kept things simple and easier for the team to reason about, and I'm cautious about introducing NgRx's boilerplate/ceremony before the complexity actually justifies it.

- Explain change detection — default vs. OnPush. How have you used OnPush to fix performance issues?
  - Angular's default change detection strategy checks every component in the tree, top to bottom, whenever any async event happens anywhere in the app — a click, an HTTP response, a timer tick, a promise resolving. It doesn't try to figure out if a particular component's data actually changed; it just re-checks all bindings on all components every time. That's simple and safe, but it means as your component tree grows, every change-detection cycle does more work than it needs to, even for components whose data hasn't changed at all.

  - **OnPush changes that:** a component with changeDetection: `ChangeDetectionStrategy.OnPush` only gets re-checked when one of a few specific things happens:

  - an @Input() reference changes (note: reference, not deep mutation — so immutable data patterns matter here),
  - an event originates from within that component or its children (a click, etc.),
  - an observable bound via the async pipe emits a new value,
  - or you manually trigger it via ChangeDetectorRef.markForCheck().

  - So with OnPush, Angular can skip entire subtrees during a change detection cycle if their inputs haven't changed by reference, which is a meaningful performance win in a large app.

  - **Where I actually used this:** the offers and rewards list views in the app I led could render a fair number of rows — offer lists, and especially the bulk-registration results screen, which shows potentially hundreds of records with their success/failure status after a batch upload completes. With default change detection, every polling tick checking upload status, or every unrelated action elsewhere in the app, was triggering a full re-check of that entire rows list, even though most rows hadn't changed. That showed up as janky scrolling and sluggish UI updates during an active bulk upload, when polling was firing every few seconds.

  - I switched the list and row components to OnPush, and paired it with a few supporting changes that OnPush requires to actually work correctly:

  - Made sure data passed into those components was treated immutably — instead of mutating an array in place when new status came in, I created a new array/object reference so Angular's reference check would actually pick up the change.
    Used the async pipe directly in the template wherever possible, bound to observables from the status-polling service, since async pipe plays natively with OnPush and handles subscription/unsubscription for you.
    For the few places I needed an imperative update outside of an input or async-pipe emission — like after a manual retry action — I called markForCheck() explicitly to tell Angular this component needs re-checking.

  - The result was a noticeably smoother UI on the bulk-registration results screen during active polling — we cut a large amount of unnecessary change-detection work happening on every polling cycle, since only the rows management screen's outer container needed to react to the new data, not every unrelated component in the tree.

- How do you handle API error handling and retries across a large app (interceptors)?
  - I handle this centrally with `HTTP interceptors `rather than repeating error-handling logic in every component or service — that's the whole point of interceptors: every outgoing request and incoming response passes through a single pipeline, so I get one place to apply cross-cutting concerns consistently across the app.

  - I typically layer a few interceptors, each with one responsibility:
  1. Auth interceptor — attaches the access token to outgoing requests, and if a response comes back 401, it tries a token refresh and retries the original request once; if refresh fails, it redirects to login. This runs first in the chain.

  2. Retry interceptor — for transient failures (network blips, 502/503/504 from a backend that's momentarily unavailable), I use `RxJS's retry` or retryWhen operator with an exponential backoff — say retry up to 2-3 times with increasing delay — rather than retrying instantly in a tight loop. Importantly, I only retry idempotent requests — GETs, and PUT/DELETE where safe — never blindly retry a POST that creates a resource, since that risks duplicate offers or duplicate registrations. That distinction mattered a lot in this app specifically: bulk registration and offer-creation are POST operations, so I was deliberate about not auto-retrying those at the interceptor level — a failed registration call needed to surface to the rep rather than silently retry and risk a duplicate enrollment.

  3. Error interceptor — catches errors that fall through (after retries are exhausted, or on non-retryable errors) and normalizes them into a consistent shape before they reach the component: extracting a user-friendly message from the backend's error response contract, logging/reporting unexpected errors (5xx, unknown format) to our monitoring tool, and for things like 403s, redirecting or showing a permission-denied state rather than a generic error toast.

  4. Loading/notification interceptor (sometimes combined with the error one) — surfaces a consistent toast/snackbar for errors app-wide, so a component author doesn't have to remember to wire up error UI every time they call an API — they just subscribe and handle the success case; the interceptor guarantees the failure case is visibly communicated to the rep.
  - Where this specifically mattered for the bulk-registration flow: the status-polling calls I mentioned earlier are GETs firing every few seconds, so those are safe to retry on transient failure without any real risk — if one poll fails due to a network blip, the retry interceptor just quietly retries and the rep never notices. But the actual file-upload-triggered registration call is a POST with real side effects, so that error needs to surface plainly — in that flow, I made sure failures showed up in the per-record success/failure summary I mentioned, rather than being swallowed by a generic retry.

  - One more thing I enforce: interceptors should be side-effect-consistent but not swallow errors silently. Even after handling/normalizing, I still re-throw the error (or an error-shaped object) so the calling component or service can react appropriately — e.g., stop a loading spinner, or block a form submit button — rather than the interceptor fully absorbing it and leaving the UI in an inconsistent state.

- Component communication patterns: @Input/@Output vs. shared services vs. state store — how do you decide?
  - I think of this as a decision that scales with how far apart the two pieces of state are in the component tree, and how many places need to react to a change — not a one-size-fits-all choice.

  - @Input() / @Output() — my default for direct parent-child communication. It's explicit, easy to trace, easy to test in isolation, and doesn't add any indirection. In the offers app, this is how a list-item row component tells its parent list "I was clicked" or "toggle my status," or how a parent passes a single offer record down into a detail/edit component. If the relationship is a direct line — one parent, one or a few children — @Input/@Output is almost always right. The moment you're passing data down three or four levels through components that don't themselves care about that data (prop drilling), that's my signal to stop using inputs and reach for a shared service instead.

  - **Shared services (with RxJS)** — my default for anything that needs to be shared across components that aren't in a direct parent-child relationship, or across module boundaries, without the complexity of a full state-management library. In this app, that's things like: the current rep/session info needed by both the Offers and Rewards modules, or the shared reward-lookup data I mentioned earlier that both offer-creation and reward-management screens need. I'd provide the service at the appropriate level — `providedIn: 'root'` for truly app-wide singletons, or provided at a module level if I want scoped state per lazy-loaded feature — and expose state via `BehaviorSubjects` so components can subscribe and get both the current value and future updates. This is my default reach when the alternative is prop-drilling or duplicating an HTTP call in multiple components.

  - **A full state store (NgRx)** — I reserve this for real complexity: many components across the app reading and writing overlapping state, non-trivial async orchestration where you want a predictable single source of truth, or when I need dev tooling like time-travel debugging and strict traceability of every state change for a large team to reason about. For this offers/rewards app specifically, I didn't introduce NgRx — the shared-service-with-RxJS pattern covered our needs without the added boilerplate and the ramp-up cost for every developer touching the codebase. If the app had grown to where, say, an in-progress bulk-registration job's status needed to be reflected simultaneously in a header notification badge, a dashboard widget, and the results screen, all updating consistently and possibly with optimistic UI or undo — that's the point I'd seriously consider NgRx, because at that level of fan-out, a bag of services each with their own BehaviorSubject starts getting hard to reason about and easy to get inconsistent.

  - So the short version of how I decide: start with @Input/@Output for direct relationships, move to a shared service the moment you're drilling props through indifferent intermediate components or need cross-module state, and only reach for a full state store when the number of consumers and the complexity of the interactions between them genuinely justifies the overhead — not by default, and not just because it's a common pattern people reach for.

  - **Have you ever regretted not using NgRx,** or regretted introducing it?" — a good honest answer is to say you've seen teams over-engineer with NgRx too early, which adds actions/reducers/effects boilerplate for state that a service could've handled, and that you'd rather introduce it deliberately when the complexity is real than default to it. If you have a genuine example of either scenario, use it here — real war stories land well in a lead interview

- How do you structure a large-scale Angular app for a team of multiple developers (folder structure, shared component library)?
  - As a lead, my goal with folder/module structure is that a new developer — or a contractor coming in for a few weeks — can find where something belongs without asking me, and two developers can work on different features simultaneously without stepping on each other's files or merge-conflicting constantly.

  - High-level folder structure I use:

  src/app/
  core/ -> singletons: auth, interceptors, guards, app-level services
  shared/ -> reusable, stateless: components, pipes, directives, models
  features/
  offers/ -> offers module (components, services, routing — self-contained)
  rewards/ -> rewards module
  bulk-registration/ -> bulk upload module
  layout/ -> shell/nav/header components used across features
  - Each feature folder is self-contained — its own components, services, models, and routing module, lazy-loaded independently. This is deliberate: it means two developers working on Offers and Rewards respectively are almost never touching the same files, which cuts down merge conflicts and lets people work in parallel without a lot of coordination overhead. It also means a feature can be reasoned about, tested, and even deleted or rewritten in isolation without touching unrelated code.

  - Shared component library: for common UI — buttons, modals, the file-upload widget used in bulk registration, form field wrappers, data tables — I pulled these into a shared module (or for a bigger org, an actual separate library via Angular's ng generate library, published internally via a private npm registry or Nx workspace). The reasoning: the offers list, rewards list, and any future feature all needed the same table/pagination/status-badge components, and I didn't want three slightly-different implementations drifting apart. A shared library also forces an interface contract — inputs/outputs are documented and stable — so consuming teams aren't reaching into internals.

  - Conventions I enforce as a lead, beyond folder structure:
    - Consistent naming — feature/component/service naming conventions documented so people aren't guessing (offer-list.component.ts vs OfferListComponent, etc.), enforced partly via `lint rules`.
    - A style guide and lint/prettier config checked into the repo and enforced in CI, so code review isn't spent on formatting bikeshedding.
    - Barrel files (index.ts) at the shared-library and feature-module level, so consumers import from a clean public path rather than reaching into internal folders.
    - A documented contract for how features talk to each other — i.e., only through shared services or well-defined inputs/outputs, never one feature module importing directly from another feature's internals. That's a rule I'd actually enforce in code review, because otherwise you get hidden coupling between, say, Offers and Bulk Registration that makes them hard to change independently later.

  - For a multi-developer team specifically, I also think about:
    - Ownership boundaries — even without formal microservice-style ownership, I'd informally assign feature modules to specific developers/pairs so there's a clear point of contact and consistent style within each module.
    - Testing conventions — a documented pattern for how to test a component/service (what's unit-tested vs. what needs an integration/e2e test), so coverage doesn't depend on individual developer habits.
    - A generator/schematic or a documented template for 'how to add a new feature module' — so a new feature starts from a consistent skeleton (routing, module file, folder layout) rather than everyone improvising their own structure.

    - In practice, on the offers/rewards app, this structure meant that when we added the bulk-registration feature later, it slotted in as a new lazy-loaded module reusing the shared upload widget and shared services, without needing to touch the Offers or Rewards modules at all — which is really the test of whether the structure is working: can you add a new capability without ripple effects across the rest of the app.

    - **Likely follow-up to have ready:** How do you enforce these conventions across a team — code review alone, or tooling?" — good answer: a mix — lint rules and CI checks catch mechanical stuff automatically (so review isn't wasted on style), and code review focuses on the things tooling can't catch: whether a piece of logic belongs in shared vs. feature, whether a new coupling between modules is being introduced, etc. If you've used Nx workspace boundaries (enforceModuleBoundaries lint rule) to technically prevent one feature from importing another's internals, that's a strong concrete detail to drop here — it shows you don't just document the rule, you make it unbreakable.

- Authentication/authorization in Angular — route guards, token refresh, interceptor-based auth headers.
  - MSAL handles the Angular application's own login/session, while a separate Spring Boot auth server issues the bearer tokens actually used for our backend API calls. They're related but not the same token.

  - **Login and route guards (MSAL):** For the Angular app itself, we use MSAL — @azure/msal-angular — for the rep's login flow against Azure AD/Entra ID, and MsalGuard on protected routes/feature modules so an unauthenticated rep is redirected into the Azure AD login flow before reaching Offers, Rewards, or Bulk Registration. For role-based access beyond just 'is this rep logged in,' I layered a custom guard that checks role/claims to gate specific routes — like restricting bulk registration to reps with the right permission.

  - Getting the bearer token for API calls (separate token endpoint): For calling our Spring Boot backend, we don't use the MSAL-issued token directly. Instead, after MSAL confirms the rep is authenticated, the app calls a dedicated token endpoint on our own Spring Boot auth server, which issues a bearer token scoped for our API. Practically, that's often done by exchanging the MSAL identity (e.g., passing the MSAL ID token or the authenticated user's identity) to that token endpoint, which validates it and returns back our own application-issued access token — so the backend APIs trust and validate tokens issued by our own auth server, not Azure AD tokens directly. This decouples our API's auth from being tightly bound to Azure AD's token format/claims, and lets the backend define its own token contract, scopes, and expiry policy independent of the identity provider.

  - Interceptor-based auth headers: Because of that split, I couldn't just rely on MsalInterceptor's default behavior for backend API calls — that interceptor is really meant to attach Microsoft-issued tokens against Microsoft-registered resources. Instead, I wrote a custom HTTP interceptor for our backend API calls: it holds the bearer token obtained from our Spring Boot token endpoint (cached in a service, typically an in-memory/BehaviorSubject-backed token store, not localStorage, to reduce exposure), attaches it as the Authorization header on outgoing requests to our API base URL, and — this is the important part — handles refresh/expiry for that token independently of MSAL's own token lifecycle. MSAL still silently renews the rep's Azure AD session in the background per its own schedule, but our custom interceptor is responsible for noticing when our application token is close to expiry (or gets a 401 back from the backend) and re-calling the Spring Boot token endpoint to get a fresh one before retrying the original request.

  - Token refresh flow, concretely: the interceptor checks token expiry before attaching it to a request; if it's expired or close to it, it calls the token endpoint first, updates the cached token, then proceeds with the original request. If a request still comes back 401 despite that — say the backend token was revoked server-side — I handle that as a hard auth failure: clear the cached token, and either silently re-fetch once as a retry, or if that also fails, treat it as a session problem and route the rep back through login (which re-triggers the MSAL flow if their Azure AD session itself has also lapsed).

  - Why I mention this distinction explicitly when I design a system like this: it would've been simpler to just pass the MSAL access token straight through to Spring Boot and validate Azure AD tokens on the backend directly — and for some apps that's the right, simpler choice. But having our own token-issuing endpoint gives the backend control over its own token contract (custom claims, its own expiry/refresh policy, ability to add app-specific authorization info to the token) without being coupled to whatever Azure AD happens to put in its tokens — which matters more as the backend serves multiple frontends or needs claims that don't map cleanly to Azure AD's token shape."\*\*

  - Likely follow-up to have ready: "Why have a separate token-issuing server instead of just validating the MSAL/Azure AD token directly in Spring Boot?" — the answer above covers this, but be ready to also acknowledge the trade-off honestly if pushed: it's an extra moving part (another token endpoint to secure, another token lifecycle to manage) versus the simplicity of just validating Azure AD tokens with Spring Security's OAuth2 resource-server support directly. A good lead answer shows you see both sides, not just defends the existing design blindly.

- How do you approach testing (unit with Jasmine/Karma, e2e) and how much coverage do you enforce as a lead?
  - My approach to testing is layered — I don't treat 'coverage %' as the goal in itself, I treat it as a signal that tells me whether the important paths are actually protected. Chasing a number leads to shallow tests that assert nothing meaningful just to touch a line.

  - Unit tests (Jasmine/Karma): These are the bulk of the test suite — fast, isolated, run on every commit/PR. What I prioritize testing at the unit level:

  - Services — especially anything with real logic: the token-refresh logic I mentioned earlier, the shared reward-lookup service, the status-polling logic for bulk registration. These are pure-ish and easy to mock HTTP dependencies for, so they're cheap to test thoroughly and high-value, since a bug here silently affects every consumer.
  - Components with logic — anything beyond a dumb template: form validation logic on the offer-creation form, the bulk-upload results component's success/failure summary logic, guard logic (role checks). I use TestBed with shallow rendering where possible, and mock child components/services rather than pulling in the whole tree.
  - Pipes and utility functions — cheap, deterministic, no excuse not to have high coverage here.
  - What I don't spend much unit-test effort on: pure presentational/dumb components with no logic — a component that just binds @Input values to a template doesn't need heavy unit tests; that's better covered by a quick smoke test (renders without erroring) or left to e2e/visual coverage instead.

  - Integration-style tests: Between pure unit and full e2e, I also write tests that exercise a feature module's components together with real (or realistically mocked) services — e.g., does the offer-creation form actually call the right service method with the right payload when submitted, does the bulk-upload component correctly reflect a service's status updates over time (using Angular's fakeAsync/tick to simulate the polling flow). This layer catches wiring bugs that isolated unit tests miss but that don't need a full browser.

  - E2E: I keep this focused on the critical business flows end-to-end, not exhaustive coverage of every screen — e2e is slow and comparatively brittle, so I don't try to make it do unit tests' job. For this app, the e2e suite covers things like: rep logs in → creates an offer → offer appears in the list; and the bulk-registration happy path — upload a file → see status progress → see success/failure summary. I'd also cover at least one realistic failure path e2e — e.g., uploading a malformed file and confirming the rep sees a clear error — since that's exactly the kind of thing that looks fine in isolated unit tests but breaks when the real S3/Lambda pipeline is involved.

  - Coverage enforcement as a lead: I don't chase a single global number like '80% everywhere' — I set a reasonable floor (commonly 70-80% for services/business logic) enforced in CI so a PR can't silently drop coverage, but I care more about what's covered than the percentage. I'd rather have 100% coverage on the token-refresh interceptor and the bulk-upload status logic — because bugs there are expensive and hard to notice — than have inflated coverage from testing trivial getters. In code review, I look at whether new logic has a meaningful test, not just whether the coverage report is green; a developer can write a test that executes a line without actually asserting the right behavior, and coverage tooling won't catch that, but review will.

  - One practical thing I enforce for a rep-facing internal tool specifically: any bug that's caused a real incident gets a regression test added as part of the fix — non-negotiable. That's how the suite actually stays relevant to real failure modes rather than being written once at feature-build time and never updated."\*\*

  - Likely follow-ups to have ready:
    - "How do you test the S3/Lambda part of the bulk-registration flow, since that's outside Angular?" — good answer: that's out of scope for Angular's own test suite; on the Angular side I'd mock the API/status responses to test the UI's handling of various states (in-progress, partial failure, full failure), and rely on separate backend/integration tests (or a Lambda-specific test harness) to verify the S3→Lambda→registration-API path itself — Angular tests shouldn't be asserting on backend behavior they don't own.
    - "What's your opinion on TDD?" — safe honest answer: pragmatic, not dogmatic — TDD for genuinely tricky logic (e.g., the token refresh queuing behavior) where thinking through test cases first clarifies the design, but not treated as a rule for every trivial component.

- Performance: how do you diagnose and fix a slow-rendering Angular page?
  - I approach this as two phases — diagnose first, don't guess-and-fix — because performance problems that look similar can have completely different root causes.

  - Diagnosis:

    - Reproduce and measure first. Chrome DevTools Performance tab — record a trace while triggering the slow interaction (e.g., loading the offers list, or the bulk-registration results screen with a large record set), and look at where time is actually going: is it scripting (change detection, component logic), rendering/layout, or network waiting?
    - Angular DevTools profiler — this is the more targeted tool. It shows exactly which components are being checked on each change-detection cycle and how long each takes. This is usually where I find the real culprit — e.g., a components tree being re-checked far more often than it should, or one specific component's ngOnChanges/template doing expensive work repeatedly.
    - Check the Network tab — sometimes 'slow rendering' is actually 'slow data,' not a rendering problem at all. If the offers list feels sluggish because the API call itself takes 3 seconds, that's a backend/API problem, not something OnPush or track-by will fix — I want to rule this out early so I don't waste time optimizing the wrong layer.
    - Bundle analysis (webpack-bundle-analyzer or Angular's built-in stats) if the issue is more about slow initial load than slow interaction — checking whether a feature module pulled in something heavy it shouldn't have (a large third-party library imported eagerly instead of lazy, e.g.).

  - Common root causes I look for, and fixes:

    - Change detection running too often / checking too much — this is the most common one. Fix: switch relevant components to ```OnPush``` (as I described earlier for the bulk-registration results list), paired with ```immutable data updates and the async pipe```, so Angular skips subtrees that haven't changed.
    - Expensive work inside a template binding — calling a function directly in a template ({{ calculateTotal(offer) }}) re-runs that function on every single change-detection cycle, even if nothing relevant changed. Fix: move that into a memoized value, a computed property set once when the underlying data changes, or a pure pipe — pure pipes only re-run when their input reference changes, which is a cheap win.
    - Missing trackBy on \*ngFor — without it, Angular re-renders every DOM node in a list on any change to the array reference, even if only one row actually changed, which destroys and recreates DOM nodes unnecessarily. This mattered directly in the bulk-registration results screen — potentially hundreds of rows updating as status comes in. Adding trackBy keyed on a stable record ID meant Angular could diff and only touch the rows that actually changed, not tear down and rebuild the whole list on every status update.
    - Large lists rendered all at once — for something like the bulk-registration results with a large record count, beyond trackBy I'd also consider virtual scrolling (Angular CDK's cdk-virtual-scroll-viewport) so only the visible rows are actually rendered in the DOM, rather than all hundreds of rows existing at once regardless of viewport.
    - Too much work in lifecycle hooks — ngOnChanges/ngDoCheck doing heavy computation on every cycle. Fix: move heavy computation out of hooks that fire frequently, cache/memoize results, or restructure so the computation happens once when the source data actually changes.
    - Unnecessary subscriptions/re-subscriptions — a component re-subscribing to an observable on every change-detection cycle instead of once in ngOnInit, or not unsubscribing and accumulating dead subscriptions over a session that slow things down over time. Fix: subscribe once, use async pipe where possible so Angular manages the lifecycle, and always clean up with takeUntil/Subscription.unsubscribe() in ngOnDestroy.

  - After the fix: I always re-measure with the same profiling tool I diagnosed with, rather than assuming the fix worked — sometimes the real bottleneck was one layer deeper than the first thing I optimized.

  - Concrete example from this app: the bulk-registration results screen was the one place we actually hit this — several hundred rows, each updating as polling brought in new status data every few seconds. The fix was a combination: OnPush on the row and list components, trackBy keyed on record ID so unaffected rows weren't torn down and rebuilt, and switching the status update from replacing the entire array reference on every poll to only replacing the specific rows that changed (still creating new references for changed rows to satisfy OnPush, but leaving unrelated row object references untouched) — which meant far fewer rows were even eligible for re-check on each cycle, not just faster checks."\*\*

  - Likely follow-up to have ready: "How do you prevent this kind of regression from creeping back in?" 
    - good answer: performance budgets/checks in CI where feasible (bundle size budgets are common and easy to add via Angular's angular.json budgets config), and treating OnPush+trackBy as a default convention on any list-rendering component from the start, rather than something retrofitted only after a complaint.
- How do you implement API integration in Angular (HttpClient, interceptors, typed services, error/retry handling)?
  - API integration in this app follows a layered pattern — I keep raw HTTP concerns out of components entirely, so components only ever talk to typed services, never HttpClient directly.

  - Typed services layer: Every feature has a dedicated service — OffersService, RewardsService, BulkRegistrationService — that wraps HttpClient calls and exposes strongly-typed methods returning typed observables, e.g. getOffers(): Observable<Offer[]>, createOffer(offer: CreateOfferRequest): Observable<Offer>. I define TypeScript interfaces/models for both request and response shapes, shared from a models folder, so a compile-time error catches a mismatch between what a component expects and what the service returns — rather than discovering a shape mismatch at runtime. This also means components never construct URLs, headers, or query params themselves; that's entirely the service's responsibility, so if an API contract changes, there's exactly one place to update it.

  - HttpClient usage: Services use HttpClient's typed generics (this.http.get<Offer[]>(url)) rather than casting any, and centralize the base API URL via environment config rather than hardcoding it per service — so switching between dev/staging/prod endpoints is a config change, not a code change.

  - Interceptors handle everything cross-cutting, which I covered in detail earlier: the MSAL-based auth for the Angular app itself, our custom interceptor for attaching the Spring Boot-issued bearer token to backend API calls, a retry interceptor for safe/idempotent requests with exponential backoff, and an error interceptor that normalizes error responses before they reach a service or component. The point of pushing all of this into interceptors is that a service method like createOffer() only has to express its own business logic — build the payload, call the endpoint, map the response — and doesn't need to know or care about auth headers, retry policy, or error formatting; that's handled once, globally, and consistently.

  - Error/retry handling at the service level: interceptors handle the cross-cutting retry/error normalization, but individual services still handle domain-specific error logic where it matters — e.g., in BulkRegistrationService, if the file-upload/presigned-URL call fails, that needs a specific user-facing message different from a generic 'offer creation failed' error, so the service (or the component consuming it) catches that specific error case using RxJS catchError and maps it to a domain-meaningful result rather than just letting the generic error interceptor's message bubble up unchanged.

  - Typed request/response models specifically matter for the bulk-registration flow — since that flow has a few distinct steps (get presigned URL → upload to S3 directly → poll status → get results summary), having a typed interface for each step's request/response (PresignedUrlResponse, UploadStatus, RegistrationResult[]) meant the component consuming BulkRegistrationService gets full autocomplete and compile-time safety across a fairly multi-step async flow, which is exactly where an untyped/any-based approach would be easy to get subtly wrong — e.g., reading a status field that doesn't actually exist on the response.

  - One pattern I enforce across all these services: methods return observables, not promises, and I never call .subscribe() inside a service — subscription happens at the point of use (a component, or the async pipe in a template), so services stay composable and testable, and it's the consumer's responsibility to manage subscription lifecycle (or let async pipe handle it), not the service's."**

- How do you handle environment-specific configuration in Angular (environment.ts files, build-time replacement)?
  - Angular's standard approach is environment.ts files with build-time replacement, and I follow that pattern but I'm deliberate about what actually belongs there versus what shouldn't.

  - Standard setup: a base environment.ts (used for local dev by default) and per-environment overrides — environment.dev.ts, environment.staging.ts, environment.prod.ts — each exporting the same interface/shape so there's compile-time safety that every environment defines the same set of config keys. The angular.json file maps each build configuration (ng build --configuration=staging) to a fileReplacements entry, so at build time Angular's builder swaps in the right file — the app never checks process.env or does runtime branching on environment; it's resolved once, at compile time, so there's zero chance of a dev config accidentally shipping active in a prod bundle at runtime.

  - What goes in there for this app specifically: API base URLs (the Spring Boot backend's base URL differs per environment), the MSAL configuration — client ID, tenant/authority URL, redirect URI — since those differ between our dev/staging Azure AD app registration and the prod one, feature flags if we have any environment-gated features, and things like logging verbosity (verbose in dev, minimal in prod).

  - What I explicitly keep OUT of environment files: any actual secret — API keys, client secrets, signing keys. Environment files ship inside the compiled JS bundle to the browser, so anything in there is fully visible to anyone who opens dev tools — it's client-side config, not a secrets store. MSAL's client ID is fine to have there because it's a public identifier by design (OAuth2 public client), but if I ever saw someone about to put a client secret or an API key with real privileges into an environment.ts file, that's a hard stop — that belongs server-side, never shipped to the browser.

  - CI/CD integration: the build configuration is chosen by the CI pipeline based on the target environment/branch, so promoting a build from staging to prod isn't a rebuild with different environment files swapped in by hand — the pipeline picks the right --configuration flag automatically based on deployment target, which avoids a class of human error where someone manually edits environment.ts before a prod deploy and forgets to revert it.

  - One nuance I'd flag if asked about scaling this pattern: build-time replacement means a config change requires a rebuild and redeploy — you can't just flip an environment value without shipping a new build. For anything that genuinely needs to change without a redeploy — a feature flag that ops wants to toggle live, for instance — I'd move that out of environment.ts and into an actual runtime-fetched config (a small config.json fetched on app bootstrap, or a feature-flag service call) rather than trying to force build-time config to do a runtime config's job."**

- How do you implement offline capability in Angular (Service Workers, Angular PWA support, IndexedDB/localStorage for local caching)?
  - I haven't had a hard requirement to build full offline support in my recent projects — the apps I've led, like the offers/rewards tool, are used by reps on the corporate network, so it wasn't a real business need. But I know the toolset and how I'd approach it if a requirement called for it, say for reps working from branch locations with unreliable connectivity.
  - The standard approach in Angular is @angular/pwa, which sets up a Service Worker via Angular's ngsw-config.json. The service worker sits between the app and the network and can cache the app shell (JS/CSS/HTML bundles) so the app itself loads even with no connection, plus configurable data-caching strategies for API calls — freshness-first (try network, fall back to cache) or performance-first (serve cache immediately, revalidate in background), configured per API route pattern in ngsw-config.json.
  - For actual data that needs to be usable offline — not just cached API responses, but data a user might create or edit while offline — I'd reach for IndexedDB rather than localStorage, since localStorage is synchronous, has a small size limit, and isn't well-suited for structured data; IndexedDB handles larger, structured, queryable data properly and works asynchronously so it doesn't block the UI thread. I'd typically use a wrapper library like Dexie.js or ngx-indexed-db rather than the raw IndexedDB API, since the raw API is verbose and easy to get wrong.
  - Architecturally, I'd put a repository-style abstraction in front of both the network and IndexedDB — a service that decides 'do I have this in local cache, is it fresh, do I need to hit the network' — so components never know or care whether they're getting live or cached data; they just consume an observable.
- How do you keep an Angular application functional when the backend server is unavailable (cached responses, optimistic UI, queuing failed requests)?
  - Same caveat — I haven't built this specific pattern in production, but I can walk through how I'd design it.
  - First layer: cached responses. For read-heavy data — lists, lookups — the service worker or an IndexedDB-backed cache serves the last-known-good response when the network call fails, so the UI degrades to 'showing slightly stale data' rather than a hard error or blank screen. I'd make that visible to the user — a subtle banner or indicator saying data may be outdated — rather than silently pretending it's live, since especially for something like offer/reward data, silently showing stale data without telling the rep could lead to a bad decision.**
  - Second layer: for writes (creating/editing something) while offline, the two realistic options are:
  - Block the action with a clear 'you're offline, this action requires a connection' message — simplest, safest, and often the right call for anything with real side effects, like creating an offer or triggering a registration, where an optimistic write that later fails to sync could cause real confusion or duplicate records.
  - Optimistic UI + queue — update the local UI immediately as if the action succeeded, queue the actual request (in IndexedDB) to be sent once connectivity returns, and reconcile if the eventual real request fails. This gives a much better UX but adds real complexity — you need to handle the case where the optimistic update turns out to be wrong (rejected server-side), and you need a way to visually distinguish 'pending/unsynced' from 'confirmed' state so the user isn't misled into thinking a write has actually completed.**
  - I'd detect connectivity using the browser's navigator.onLine plus window.addEventListener('online'/'offline') — though I'd treat navigator.onLine as a hint, not a guarantee, since it can report 'online' even when a specific request still fails (e.g., connected to WiFi but the actual API is unreachable), so I'd still handle request-level failures independently of that flag.
  - For this specific kind of app — offers and rewards, with real business/financial-adjacent consequences — I'd lean toward blocking writes rather than optimistic-queuing them, unless there was a strong, specific business case for offline writes. The risk of a rep believing a reward was granted, when it was actually silently queued and later failed to sync, outweighs the UX convenience — I'd rather have a clear 'you're offline, try again once connected' than a UI that lies about state, even briefly."
- How do you synchronize or merge offline data once the application comes back online (conflict resolution, background sync, retry queues)?
  - Continuing from the queuing pattern above — once the app detects connectivity restored (via the online event), it processes the queue: pulls each pending request out of IndexedDB in order, replays it against the real API, and on success removes it from the queue and reconciles the optimistic local state with the real server response (which may differ slightly from what was optimistically assumed — e.g., a server-generated ID or timestamp).
  - Background Sync API (part of the service worker platform, where browser support allows) can do this more robustly than a simple 'listen for online event' approach — it lets the browser retry a queued sync task even if the tab itself isn't open, deferring to the browser to retry when connectivity is confirmed stable, rather than the app naively firing the instant navigator.onLine flips true (which can be a false start if connectivity is still flaky).**
  - Conflict resolution is the genuinely hard part, and the right strategy depends entirely on the data: for something like a rep editing an offer's details, if the same record was also changed by someone else (or by a backend process) while the rep was offline, you generally have a few options — last-write-wins (simplest, but can silently lose someone's changes), a version/timestamp check where the server rejects a stale write and asks the client to refresh and reapply (safer, more explicit), or in more advanced cases actually surfacing a merge conflict to the user for manual resolution. For most business-data use cases I'd default to the version-check-and-reject approach rather than silent last-write-wins, specifically because silently overwriting someone else's change without them knowing is a worse failure mode than making the user redo an action.**
  - I'd also want clear UI communicating queue state — a small '2 changes pending sync' indicator — so the rep isn't left guessing whether their offline actions actually went through, and a way to see/retry a specific failed sync if the replay itself fails (e.g., the record was deleted server-side in the meantime).
  - Again, to be transparent — this wasn't something the offers/rewards app needed, so this is design-level knowledge rather than something I've operated in production. If this is a real requirement for the Schwab role, I'd want to understand the specific offline scenarios that actually happen for reps before picking a strategy — the right level of complexity here really depends on how often reps are actually offline and what they need to do while disconnected.
- How would you test a component or service that depends on offline/cached data?
  - For a component or service that depends on offline/cached data — whether that's a service worker cache, IndexedDB, or just an in-memory cache like the reward-lookup service I described earlier — my approach is to isolate the caching mechanism behind an interface so it's mockable, and then test each state of that cache explicitly rather than relying on an actual browser cache during tests.
  - Isolate the cache behind a service/abstraction: rather than a component reaching directly into localStorage, IndexedDB, or the Cache API, I wrap that behind a small service with a clear interface — get(), set(), has(). That means in unit tests, I can substitute a simple in-memory fake or a Jasmine spy for that service, rather than needing an actual browser storage API available in the test environment (which is often unreliable or slow in a test runner like Karma/Jest).
  - Test the distinct states explicitly, as separate test cases:
  - Cache hit, data fresh — component/service should use cached data without hitting the network at all; assert the HTTP mock was never called.
  - Cache miss — should fall through to a network call, and populate the cache afterward; assert both the network call happened and the cache-set method was called with the right data.
  - Cache present but stale/expired — depending on the caching strategy, either serve stale data immediately while revalidating in the background (stale-while-revalidate), or treat it as a miss — whichever the actual design is, that behavior needs its own explicit test rather than being implied.
  - Offline / network failure — simulate the HTTP call failing (via HttpTestingController.error() or a rejected observable) and assert the component falls back to cached data gracefully rather than showing a hard error, if that's the intended UX.
  - Genuinely no data available (offline AND no cache) — assert the component shows an appropriate empty/offline state rather than crashing or showing a misleading loading spinner forever.
  - For the Angular HTTP layer specifically, HttpTestingController (from HttpClientTestingModule) is what I'd use to simulate the network responses/failures deterministically in each of those scenarios, rather than hitting a real network in tests.
  - If a service worker/PWA cache is involved, that's genuinely harder to unit test meaningfully since it's a browser-level API — for that layer I'd lean more on e2e/integration testing with tools that can simulate offline mode (Cypress and Playwright both support toggling network conditions/offline mode), rather than trying to force it into a Karma/Jasmine unit test.
  - Honestly, for this specific app — the offers/rewards tool — we didn't build offline support; it's used by reps who are on the corporate network throughout their shift, so it wasn't a real requirement, and I'd be cautious about adding that complexity without a genuine business need. But the pattern above — abstracting the cache, testing each state as an explicit case, using HttpTestingController to simulate failure — is exactly how I'd approach it if a future requirement called for it, say if reps needed to work in low-connectivity branch locations."

## APIs

- What are the different ways to communicate with APIs (REST, GraphQL, gRPC, WebSockets, messaging/event-driven) — when have you chosen one over another?
  - There are a handful of major patterns, and I pick based on the shape of the interaction — request/response vs. streaming, how tightly coupled the client and server need to be, and latency/throughput requirements.
  - REST — my default for most CRUD-style, request/response interactions, which is the vast majority of what the offers/rewards app needs: create an offer, fetch a list, update a reward. REST's strengths are simplicity, wide tooling support, easy caching (HTTP semantics), and it's the lowest-friction choice for a typical Angular-frontend-talking-to-Spring-Boot-backend setup — every developer on the team already knows it, which matters for a contracting/lead role where you want the team to move fast without a steep learning curve on the wire protocol itself.
  - GraphQL — I'd reach for this when the frontend has significantly varied data-fetching needs across different views, and REST would otherwise mean either over-fetching (getting more fields than a view needs) or under-fetching (needing several round-trips to assemble one view's data) — GraphQL lets the client specify exactly the shape of data it needs in one request. I haven't needed it for the offers/rewards app since the data shapes are fairly well-defined and stable per screen, but I'd consider it for a more complex, aggregation-heavy dashboard-style app pulling from many different backend sources into one view.
  - gRPC — I'd choose this for service-to-service communication where performance matters more than human-readability — gRPC's binary protocol (Protobuf) and HTTP/2 multiplexing make it meaningfully faster and lower-overhead than REST/JSON for high-throughput internal service calls. It's not something I'd expose to a browser client directly (browser gRPC support is limited/awkward), so it's specifically an internal microservice-to-microservice choice, not something relevant to the Angular-to-backend edge of this app.
  - WebSockets — for genuinely real-time, bidirectional communication where the server needs to push updates to the client without the client polling — live dashboards, chat, collaborative editing. I mentioned earlier that for the bulk-registration status updates in the offers app, I deliberately chose polling over WebSockets, because the update frequency (every few seconds) and single-user-watching-their-own-upload nature of that flow didn't justify the added infrastructure and connection-management complexity of WebSockets. If instead we had, say, a shared operations dashboard where many reps or ops staff needed to see registration status update live and simultaneously, that tips the calculus toward WebSockets or server-sent events.
  - Messaging/event-driven (Kafka, SQS/SNS) — this is my choice when services need to communicate asynchronously and decoupled — not a direct request expecting an immediate response, but 'something happened, and interested parties should react.' This is exactly the shape of the S3-to-Lambda-to-registration-API flow in the bulk-registration feature — the file landing in S3 triggers an event, and processing happens asynchronously rather than the Angular app making a long-blocking synchronous call and waiting for hundreds of records to process. More broadly in a microservices architecture, I'd use Kafka specifically when multiple downstream services need to react to the same event independently (event fan-out), or when I want to decouple a service's availability from its consumers' — a producer doesn't need consumers to be up and healthy at the moment of publishing, unlike a direct REST call which fails if the callee is down.
  - How I decide, in short: REST is the default until there's a specific reason to deviate — a real fan-out/decoupling need points to messaging, a genuine low-latency internal service-to-service need points to gRPC, highly variable client data-shape needs point to GraphQL, and genuine real-time bidirectional push needs point to WebSockets. I try not to reach for the more complex option just because it's more sophisticated-sounding — REST plus, where appropriate, an event-driven layer for async work has covered essentially everything this app needed."**
  - Likely follow-up to have ready: "Have you used gRPC or GraphQL in production, even if not on this app?" — answer honestly based on your actual experience; if you haven't, it's fine to say so and pivot to "but I understand the trade-offs and would be comfortable adopting either if the use case called for it"
- How do you handle REST API integration end-to-end between Angular and Spring Boot (DTO contracts, versioning, CORS, error response shape, interceptors on the Angular side vs. `@ControllerAdvice` on the Spring side)?
  - I think about this end-to-end as a contract between two independently deployed pieces, so the goal is that either side can evolve without silently breaking the other — that shapes every decision below.
  - DTO contracts: On the Spring Boot side, I never expose JPA entities directly over REST — every endpoint has dedicated request/response DTOs, decoupled from the persistence model, so a database schema change doesn't automatically become an API-breaking change, and so I control exactly what's exposed (no accidentally leaking internal fields). On the Angular side, I mirror those with TypeScript interfaces in the typed services I described earlier — Offer, CreateOfferRequest, RegistrationResult, etc. Ideally these are generated from the backend's OpenAPI/Swagger spec rather than hand-maintained on both sides, since hand-maintained mirrored types drift silently — someone changes a field name on the backend and the frontend interface goes stale with no compiler error until it fails at runtime. Where I didn't have codegen in place, I'd at minimum push for it as an improvement, since it turns a runtime contract mismatch into a build-time one.
  - Versioning: For a contract this actively used by one specific frontend I own, I lean toward backward-compatible evolution over hard versioning where possible — adding new optional fields rather than changing/removing existing ones, so old and new frontend builds can both talk to the same backend during a rollout. Where a genuine breaking change is unavoidable, I'd version the endpoint itself — URI versioning (/api/v2/offers) is the simplest and most explicit approach, easy for both sides to reason about, versus header-based versioning which is more elegant but harder to debug/observe. For an internal app with one frontend consumer, I try to avoid needing hard versioning altogether by just coordinating frontend/backend deploys — but for a broader platform serving multiple frontends, real versioning discipline matters more.
  - CORS: Since Angular and Spring Boot are separate deployments (different origins, especially across environments — different hosts per environment as we discussed with the ingress config), CORS has to be configured explicitly on the Spring Boot side — a CorsConfigurationSource bean or @CrossOrigin restricting allowed origins to our actual known frontend hosts (not * — that's a real security gap I'd flag in review, especially with bearer tokens involved), allowed methods, and importantly allowing the Authorization header through, since that's how our bearer token is sent. I keep the allowed-origins list environment-specific, tied into the same environment config pattern as everything else, rather than hardcoded.
  - Error response shape: I standardize on one consistent error response contract across every endpoint — something like { timestamp, status, error, message, path, and optionally a fieldErrors list for validation failures } — and enforce that centrally on the Spring Boot side with @ControllerAdvice / @ExceptionHandler, so every exception thrown anywhere in the app — validation failures, not-found, unauthorized, unexpected 500s — gets mapped to that same consistent shape before it ever reaches the client, rather than each controller handling its own error formatting inconsistently. That consistency is what makes the Angular-side error interceptor I described earlier actually work well: it can reliably parse error.message or error.fieldErrors because it knows every backend error looks the same, regardless of which endpoint or exception type triggered it.
  - Interceptors (Angular) vs. @ControllerAdvice (Spring) — how these two layers divide responsibility: they're solving the same kind of problem — centralizing cross-cutting concerns instead of repeating logic everywhere — but on opposite sides of the wire, and I'm deliberate about not duplicating logic between them.
  - @ControllerAdvice on the backend is the source of truth for what an error looks like — it converts any exception into the standardized error DTO. That's backend-owned; the frontend should never need to guess at or work around inconsistent backend error shapes.
  - The Angular error interceptor is responsible for what the app does with that already-standardized error — extracting the message for UI display, logging/reporting to monitoring, deciding whether to retry, redirect to login on 401, etc. It's not trying to interpret messy, inconsistent errors — it can be simple and reliable precisely because the backend already guarantees a consistent shape.
  - That division is deliberate: if error formatting logic leaked into the frontend (parsing different shapes per endpoint, string-matching on error messages), it would be fragile and duplicate work across every service consumer. And if the frontend tried to fully replace backend validation with only client-side checks, that's a real security gap — client-side validation is UX, server-side validation via @ControllerAdvice-driven responses is the actual enforcement, since the API needs to be safe to call directly, not just safe when called through our Angular app.**
  - Putting it together for a concrete flow — creating an offer: Angular's OffersService.createOffer() sends a typed CreateOfferRequest DTO; Spring Boot validates it (Bean Validation annotations), and if invalid, @ControllerAdvice catches the MethodArgumentNotValidException and returns the standard error shape with field-level messages; the Angular error interceptor catches that, and the offer-creation form component maps fieldErrors onto the relevant form controls so the rep sees exactly which field needs correction — rather than a generic 'something went wrong' message."*
  - Likely follow-up to have ready: "How do you handle a scenario where the frontend and backend need to deploy independently and might be temporarily on different contract versions?" — good answer: this is exactly why I favor additive/backward-compatible changes over breaking ones where possible, and why DTOs are decoupled from internal models — a new optional field being added doesn't break an older frontend build still running during a rolling deploy, whereas removing or renaming a field would
- How do you handle idempotency for a POST/PUT API that might be retried (idempotency keys)?
  - This is actually a very real concern in the app I led — the bulk-registration flow has a Lambda calling a registration API per record after a file lands in S3, and Lambda's execution model means a function invocation can be retried (Lambda retries on certain failures, or a message can be redelivered from an SQS trigger) — so that registration POST call could genuinely fire more than once for the same record. Without idempotency handling, that's a direct path to duplicate registrations, which is a real business problem, not just a theoretical one.
  - The standard pattern is an idempotency key — a unique identifier generated by the client (or in our case, generated deterministically by the Lambda per record) and sent along with the request, typically as a header (Idempotency-Key) or as part of the request body. The server then guarantees that calling the same endpoint twice with the same idempotency key produces the same result as calling it once — the second call doesn't re-execute the side effect; it either returns the original response, or explicitly signals 'already processed.'
  - How I'd implement that on the Spring Boot side: before processing the request, check whether that idempotency key has been seen before — typically backed by a fast lookup store (Redis, or a dedicated idempotency-keys table with a unique constraint on the key). If it's a new key, process the request normally, and store the key along with the response (or at least the outcome/result ID) with an expiry — you don't want to keep every idempotency key forever, just long enough to cover the realistic retry window. If the key has already been seen, skip reprocessing and return the previously stored response directly, so the caller gets a consistent result whether it's the first or fifth attempt.
  - Where the idempotency key comes from, concretely for the bulk-registration flow: I'd generate it deterministically from something inherent to the record being registered — e.g., a hash of the batch ID plus the record's row identifier, or if the source file has a natural unique identifier per row (like an account/enrollment ID), use that directly. The important property is that retrying the exact same logical registration produces the exact same key — not a randomly generated key per attempt, which would defeat the purpose entirely, since a random key wouldn't be recognized as 'the same request' on retry.
  - For user-initiated actions from the Angular app — like offer creation, if I wanted the same protection there — the idempotency key would typically be generated client-side (a UUID) at the moment the rep clicks submit, sent with that request, and if the Angular retry interceptor (or a manual rep retry after a timeout) resends the same logical request, it reuses the same key rather than generating a new one — so even if the network was flaky and the rep's original request actually succeeded server-side but the response was lost in transit, a retry doesn't create a duplicate offer; it just gets back the original result.
  - One nuance worth mentioning: idempotency keys protect against exact retries of the same logical operation — they don't replace normal business-level duplicate detection (e.g., 'has this account already been registered for this offer, regardless of which request caused it'). I'd want both layers for something like bulk registration: idempotency keys to protect against Lambda's retry semantics causing double-processing of the same invocation, and a separate business-level check ('is this account already enrolled') to catch genuinely duplicate source data in the uploaded file itself — those are different problems even though they can look similar from the outside."**
  - Likely follow-up to have ready: "How long do you retain idempotency keys, and what happens if a legitimately new request reuses an old, expired key?" — good answer: retention window should comfortably exceed the realistic retry window for your system (e.g., 24 hours for something like Lambda retries, which typically resolve within minutes to hours) — long enough to catch real retries, short enough not to bloat storage indefinitely; and if a key legitimately gets reused after expiry, that's an edge case you accept as extremely unlikely given a well-chosen deterministic key derivation (e.g., keyed off a real business ID, not a random value that could theoretically collide)
- How do you handle pagination and rate limiting for APIs consumed by the Angular frontend?
  - These are two different problems — pagination is about efficiently delivering large result sets, rate limiting is about protecting the API from being overwhelmed — so I'll take them separately.
  - Pagination
    - On the Spring Boot side, for list endpoints — the offers list, the bulk-registration results list which can have hundreds of records — I use Spring Data's built-in Pageable/Page<T> support rather than returning an unbounded list. The client sends page number/size (and optionally sort) as query params — GET /offers?page=0&size=25&sort=createdDate,desc — and the response includes both the page of data and metadata: total elements, total pages, current page. That metadata is what the frontend needs to render pagination controls without a separate count query.
    - For very large or frequently-changing datasets, I'd consider cursor-based pagination instead of offset-based — offset pagination (page=5&size=25) can skip or duplicate records if the underlying data changes between page requests (a new record added on page 1 shifts everything else), whereas cursor-based pagination (using something like 'give me records after this ID/timestamp') is stable under concurrent writes. For most of what this app needed — reps browsing office/reward lists that don't change at high frequency — offset pagination was simple and sufficient; I'd only reach for cursor-based if the data was genuinely high-churn or the dataset huge enough that offset's performance characteristics (deep pages requiring the DB to scan/skip many rows) became a real problem.
    - On the Angular side, the typed service method takes page/size params and returns a typed page response (PagedResponse<Offer>), and the component/table handles requesting the next page — either classic numbered pagination controls, or infinite scroll depending on the UX we wanted. For the bulk-registration results specifically, since that list can be large and is often scanned top-to-bottom by a rep checking for failures, I'd lean toward virtual scrolling (Angular CDK) fetching pages progressively as the rep scrolls, rather than forcing them to click through numbered pages to find failed records.
  - Rate Limiting
    - This is primarily a backend/infrastructure concern, not something the Angular app implements — the frontend's job is to respect rate limits gracefully, not enforce them.
    - On the backend/infra side, rate limiting is typically handled at the API gateway or infrastructure layer rather than hand-rolled in every Spring Boot controller — either at an actual API gateway (Spring Cloud Gateway, or a cloud/ingress-level gateway) using a token-bucket or sliding-window algorithm, or via a library like Bucket4j or Resilience4j's RateLimiter within the Spring Boot app itself for finer-grained, endpoint-specific limits. Given the app we discussed is deployed on Kubernetes with an ingress layer, that ingress or a service mesh layer is often where coarse-grained rate limiting would actually live, keeping individual services from having to reimplement it.
    - How the Angular app handles being rate-limited: when a request gets back a 429 Too Many Requests, our error/retry interceptor needs to treat that distinctly from a generic error — ideally respecting a Retry-After header if the backend sends one, and backing off accordingly rather than immediately hammering the endpoint again. This ties directly into the retry interceptor I described earlier: the same exponential-backoff retry logic I use for transient 5xx failures is exactly the right tool for 429s too, though I'd want the backoff timing to specifically honor Retry-After when present rather than using a fixed default delay.
    - Where rate limiting specifically matters for this app: the status-polling calls during bulk registration fire every few seconds — if many reps are running bulk uploads simultaneously, or if a rep has multiple tabs open, that's a realistic source of polling load I'd want the backend protected against. I'd rather have the backend gracefully rate-limit and have the frontend back off cleanly, than have an unbounded polling pattern from many clients degrade the service for everyone.
    - One thing I'd flag as a lead reviewing a rate-limiting design: rate limits should differ meaningfully between a read-heavy polling endpoint (higher tolerance, since it's low-cost per call) and a write endpoint like offer creation or the registration call itself (lower tolerance, since each call has real side effects and cost) — a single blanket rate limit across all endpoints tends to either be too permissive on the calls that matter or too restrictive on legitimate high-frequency reads."**
    - Likely follow-up to have ready: "How would you communicate rate-limit state to the user in the UI, rather than just retrying silently?" — good answer: for anything beyond a quick automatic retry succeeding, surface a clear message ("Too many requests, please wait a moment") rather than silently retrying indefinitely and leaving the rep staring at a stuck loading spinner with no explanation — same principle as the earlier error-handling discussion: never let cross-cutting handling silently swallow a failure state the user should be aware of.
- How do you decide service boundaries — domain-driven design, bounded contexts?
  - I use domain-driven design concepts as the primary tool, but pragmatically — I care about the outcome (services that can evolve and scale independently, with minimal cross-service chatter) more than rigidly following DDD ceremony for its own sake.
  - Starting point: identify bounded contexts by language and ownership, not by technical layers. The key DDD insight I actually apply is that a bounded context is where a specific term means one consistent thing — and when the same word means different things to different parts of the business, that's usually a signal you're looking at two different contexts that shouldn't be forced into one service. In the offers platform, 'eligibility' means something distinct from 'offer definition/management' which means something distinct from 'reward issuance' — each has its own vocabulary, its own business rules, its own rate of change, and in our case, was even owned by different sub-teams with different domain expertise. That's a strong signal those should be separate services, not just separate modules in one deployable.
  - What I explicitly avoid: drawing service boundaries around technical layers (a 'database service,' a 'validation service') — that's the anti-pattern often called a distributed monolith by another name; each service should own a meaningful piece of business capability end-to-end, not be an arbitrary technical slice that still requires three services to collaborate synchronously for any single business operation to complete.
  - Signals I actually use, practically, beyond just 'what sounds like a good boundary':
  - Data ownership — does this piece of data have one clear owner? If eligibility rules and offer definitions were reading and writing the same tables interchangeably, that's a sign they're not really separate contexts yet, or that I need to think harder about which one owns that data and which one calls an API to get it.
  - Rate of change — offer eligibility rules changed frequently as the business tested new eligibility criteria; reward issuance rules changed much less often but needed much stronger consistency guarantees. Services that change at very different rates and for different reasons benefit from being deployed independently — bundling them together means a low-risk eligibility rule tweak and a high-risk reward-issuance change go through the same deployment pipeline and blast radius.
  - Team boundaries (Conway's Law, deliberately applied) — I try to align service boundaries with how teams are actually organized, since a service boundary that cuts across a team's natural ownership tends to create coordination overhead and unclear ownership. If eligibility and offer-management were owned by the same small team, I might keep them as one service initially even if DDD purism suggests splitting further — over-splitting into more services than your team can reasonably own each of independently is its own real anti-pattern, and I'd rather start slightly coarser-grained and split further later once a genuine independent-scaling or independent-team-ownership need appears, than prematurely fragment into services nobody can reason about holistically.
  - Consistency requirements — anything that needs strong transactional consistency (e.g., an operation that must atomically update both eligibility state and issue a reward, with no partial-failure window) is a strong signal those pieces might need to stay together, or if they must be separate, that I need a deliberate eventual-consistency/saga strategy rather than assuming a simple two-service call will be safely atomic.
  - Concretely, on the offers platform migration, this is exactly why eligibility, offer management, and reward issuance ended up as separate services rather than one big 'offers service' — each had a distinct owner, a distinct rate of change, and distinct consistency needs (eligibility could tolerate slightly stale data; reward issuance couldn't). But I didn't split further than that within each — e.g., I didn't create a separate microservice just for 'offer validation' as a technical slice inside offer management, since that logic doesn't have independent business meaning or an independent reason to scale or deploy on its own; it lives inside the offer-management service as a well-organized module, not a separate deployable.
  - One thing I'd actively push back on in a design discussion: service boundaries proposed purely because 'that's how DDD says to do it,' without a concrete data-ownership, team-ownership, or change-rate reason behind it. DDD is a useful lens for finding the boundaries that actually reflect the business, not a checklist to satisfy for its own sake — and getting boundaries wrong is expensive to correct later, since it usually means painful data migration and API contract changes, so I'd rather spend real discussion time getting this right upfront than move fast and re-draw boundaries constantly."**
  - Likely follow-up to have ready: "Have you ever gotten a service boundary wrong and had to fix it later?" — if you have a real example (even a small one), that's a great answer here — admitting and correcting a boundary mistake shows mature judgment more convincingly than claiming you always get it right the first time.
- How do you handle distributed transactions/data consistency across services (Saga pattern, eventual consistency, outbox pattern)?
  - Once you split a monolith's single database transaction across multiple services, you lose the ability to wrap everything in one ACID transaction — so the core question becomes: how do I get correct, consistent-enough outcomes across services without a distributed lock or two-phase commit, which don't scale well and create tight coupling between services' availability.
  - The concrete scenario I'd use from the offers platform: a reward-issuance flow that needs to (1) verify eligibility, (2) record that a reward was issued, and (3) update the customer's account/balance — potentially three different services. If step 3 fails after step 2 succeeded, I can't just roll back a distributed transaction the way I could with one database — I need a deliberate strategy for that partial-failure case.
  - Saga pattern — this is the core tool for exactly that: a sequence of local transactions, each in its own service, where each step publishes an event or triggers the next step, and critically, each step has a defined compensating action if a later step fails. So: eligibility check succeeds → reward-issuance service records the reward (local transaction, its own commit) → that triggers the account-update service to apply the balance change. If the account update fails, the saga needs to run a compensating transaction — e.g., the reward-issuance service marks that reward as reversed/failed rather than leaving it in a 'issued but never applied' state forever.
  - Choreography vs. orchestration — I pick based on how many steps and how much visibility into the overall flow I need:
  - Choreography (each service listens for events and reacts, no central coordinator) — I prefer this for simpler sagas with few steps, since it keeps services fully decoupled — reward-issuance doesn't need to know account-update exists; it just publishes 'RewardIssued' and account-update independently reacts to it via Kafka.
  - Orchestration (a central saga orchestrator explicitly calls each step and manages the state machine) — I'd reach for this once the flow has enough steps or enough compensating-action complexity that choreography becomes hard to reason about — nobody can look at one place and see the whole flow; it's implicitly spread across every service's event handlers. For anything with real financial consequences and several steps, I lean toward orchestration specifically because I want the failure/compensation logic centralized and auditable, not scattered.
  - Outbox pattern — this is the piece that makes the whole thing actually reliable, and it's a detail I'd make sure to mention because it's often the part people get wrong. The problem it solves: if a service updates its own database and separately publishes a Kafka event to notify the next step, those are two separate operations — what happens if the database commit succeeds but the Kafka publish fails (or vice versa)? You get an inconsistent state where the local data says one thing and downstream services never heard about it. The outbox pattern solves this by writing the event to an 'outbox' table in the same local database transaction as the actual business data change — so both succeed or fail atomically, since they're one transaction on one database — and then a separate process (a polling publisher, or Debezium-style CDC reading the database's transaction log) reliably publishes that outbox event to Kafka afterward, retrying until it's confirmed published. That guarantees 'the state change and the notification of that state change' are never inconsistent with each other, even though the actual publish to Kafka happens asynchronously after the transaction commits.
  - Eventual consistency — and being explicit about where it's acceptable: for something like eligibility data, I'm comfortable with eventual consistency — the eligibility service's view of an account being a few seconds stale relative to the mainframe/source system is an acceptable trade-off for the performance and decoupling benefit, especially since eligibility isn't the final gate before money moves. For reward issuance and account balance updates, I want much stronger guarantees — that's exactly why that flow needs the saga-with-compensation pattern rather than just 'fire an event and hope it eventually gets processed correctly,' since a customer's balance being wrong, even temporarily, is a much higher-severity problem than an eligibility check being briefly stale.
  - Idempotency ties directly into this — the same idempotency-key pattern I described earlier for the registration API matters just as much for saga steps and outbox-published events, since Kafka's at-least-once delivery semantics mean a saga step or an outbox-published event can be delivered/processed more than once; every step in the saga needs to be safe to process twice without double-issuing a reward or double-applying a balance change.
  - How I'd summarize the decision-making: I default to simple, synchronous request/response with normal per-service local transactions wherever a business operation genuinely lives inside one service's boundary — I don't reach for sagas by default. I introduce a saga specifically when a business operation legitimately spans multiple services' data and needs to succeed or gracefully compensate as a unit, I use the outbox pattern any time a service needs to reliably notify others of a state change alongside its own local transaction, and I'm explicit with the team about which parts of the system can tolerate eventual consistency and which genuinely can't — because treating everything as eventually consistent by default, without that distinction, is how you end up with subtly wrong financial data that's hard to detect."
- Service discovery and API gateway — how have you implemented these (Eureka, Spring Cloud Gateway, or cloud-native equivalents)?

Every service gets a stable DNS name via Kubernetes Services, and kube-proxy/the cluster's networking layer handles routing requests to healthy pod instances, including load balancing across replicas. I'd distinguish that from a full API gateway with more application-level capabilities — rate limiting, request transformation, auth enforcement at the edge — which is something I'd consider layering in (Spring Cloud Gateway, or a cloud-native API gateway) if we needed more sophisticated edge-level logic than basic routing. For our setup, most of that cross-cutting logic — auth validation, error normalization — lives in the services themselves via the patterns we've already discussed (the auth server, @ControllerAdvice), rather than centralized at a gateway layer, which was a reasonable trade-off for our scale but is exactly the kind of thing I'd revisit if the number of services and the duplication of cross-cutting logic across them grew significantly.
  - Where I'd push for an actual API gateway if it doesn't already exist: if I noticed the same cross-cutting concern (say, consistent rate limiting, or a consistent request-logging/correlation-ID injection point) being reimplemented slightly differently in each service, that's the signal to centralize it at a gateway layer instead — same principle as everything else we've discussed: push cross-cutting concerns to one place once duplication becomes a real maintenance cost, rather than centralizing prematurely before that pain is real."**

- Resilience patterns — circuit breakers, retries, timeouts, bulkheads (Resilience4j) — give a real example where this saved you.
  - Timeouts — never call a downstream dependency without a bounded wait; an unbounded call means one slow dependency can tie up your service's threads/resources indefinitely.
  - Retries — for transient failures, retry with backoff — but only for idempotent operations, as we discussed earlier, and with a capped number of attempts so retries themselves don't pile onto an already-struggling downstream service.
  - Circuit breaker — tracks failure rate for a given dependency; once failures exceed a threshold, the circuit 'opens' and stops sending requests to that dependency entirely for a cooldown period, failing fast instead of continuing to hammer something that's already struggling, then periodically tests (half-open state) whether it's recovered before fully closing again.
  - Bulkheads — isolate resources (thread pools/connection pools) per downstream dependency, so if one dependency is slow or exhausted, it can't consume all your service's threads and starve calls to unrelated, healthy dependencies — named after ship bulkheads, where one compartment flooding doesn't sink the whole ship.
  - The real scenario, during the mainframe migration: during the transition period I described earlier, our new eligibility service still depended on the mainframe as the system of record for some data that hadn't been fully migrated yet — so eligibility checks made a call out to a mainframe-fronting integration layer for that piece of data. On one occasion, the mainframe-side integration became unusually slow — not fully down, just degraded, response times went from tens of milliseconds to many seconds under some batch job contention on the mainframe side.
  - Without the resilience patterns in place, here's what would have happened: every eligibility request coming into our service would sit there waiting on that slow mainframe call, tying up request-handling threads. As more requests piled in and more threads got stuck waiting, the eligibility service itself would eventually exhaust its own thread pool and become unresponsive — even for eligibility checks that didn't actually need that specific mainframe data. That's the classic cascading-failure pattern: one slow downstream dependency takes down an entire upstream service, and then anything calling that service also starts failing, and the failure spreads outward.
  - What actually happened, because we had Resilience4j configured:
  - The timeout on that specific mainframe call was set tightly (a few seconds), so individual calls failed fast rather than hanging indefinitely.
  - The circuit breaker, configured per-dependency, tracked the failure/timeout rate for that specific mainframe call and tripped open after the failure threshold was crossed — at which point the eligibility service stopped even attempting that call for a cooldown window, and instead immediately returned a fallback response (in our case, falling back to the last-known-cached eligibility data for that data point, clearly flagged as potentially stale, rather than blocking).
  - The bulkhead meant that even while this was happening, the thread pool dedicated to the mainframe-dependent calls was the only one affected — eligibility checks that didn't need that specific mainframe data, and other endpoints on the same service entirely, kept working normally on their own separate thread pools, unaffected by the mainframe slowness.
  - Retries were deliberately NOT applied blindly here — I specifically avoided naive retry-on-timeout for this call, because retrying a call to an already-overloaded mainframe integration would have made the underlying problem worse, not better; that's a case where 'resilience' meant protecting the struggling downstream system too, not just our own service.
  - The outcome: the eligibility service degraded gracefully — some eligibility checks briefly served slightly stale cached data with that clearly communicated, rather than the whole service going down and taking dependent consumers with it. Once the mainframe-side slowness resolved, the circuit breaker's half-open state detected recovery and traffic resumed normally, with no manual intervention needed. Compare that to what would have been a full outage of the eligibility service — and by extension, anything depending on it, including reps trying to use tools built on top of it — for however long the mainframe slowness lasted.
  - What I took from that as a lead, and applied going forward: every external/downstream call — especially to legacy or less-reliable systems — gets a timeout, a circuit breaker, and its own isolated thread pool by default, not as an afterthought added after an incident. I made that a standard in our service templates rather than something each team had to remember to add individually. And I was deliberate about not blanket-applying retries everywhere — retries are the pattern most likely to make an incident worse if misapplied to a non-idempotent or already-struggling dependency, so that one gets case-by-case judgment rather than a default-on setting."**
  - Likely follow-up to have ready: "How did you decide the specific threshold/timeout values for the circuit breaker?" — good answer: started with values based on the dependency's normal observed latency/error-rate baseline (measured, not guessed), then tuned based on real incidents — e.g., after this incident, we likely tightened the failure-rate threshold or shortened the timeout further, since real production behavior is the best teacher for these values, not defaults picked off documentation
- How do you approach centralized logging/tracing across services (ELK stack, OpenTelemetry, correlation IDs)?
  - Once you've split into multiple services — especially with the resilience patterns we just discussed, where a single request might touch eligibility, a circuit breaker fallback, cached data, and potentially a mainframe integration — debugging becomes genuinely hard without centralized, correlated logging and tracing. A single user-facing request can span several services, and if each service's logs live in isolation, diagnosing a production issue turns into manually cross-referencing timestamps across sources, which doesn't scale.
  - Correlation IDs — the foundation everything else builds on. Every incoming request gets a unique correlation/trace ID generated at the edge — typically at the ingress or the first service that receives it — and that ID is propagated on every downstream call as an HTTP header. Every log line any service writes for that request includes that ID via the logging MDC (Mapped Diagnostic Context), so a servlet filter/interceptor on the Spring Boot side either reads an incoming correlation ID or generates one, puts it into MDC so it's automatically included on every log line without developers remembering to pass it explicitly, and propagates it on any outbound call the service makes.
  - Centralized log aggregation — Splunk. Every service ships structured logs (JSON, ideally, so fields like the correlation ID, service name, and log level are indexed and searchable rather than needing regex parsing over plain text) to Splunk — typically via a forwarder/agent running in the Kubernetes cluster, or a sidecar shipping container stdout logs, since in a K8s environment the standard pattern is writing to stdout and letting the platform's log-shipping layer forward that to Splunk rather than services writing directly to Splunk themselves. That means instead of checking individual pod logs one service at a time via kubectl logs, I search Splunk once: a query for a specific correlation ID pulls every log line across every service involved in that one request, in order, regardless of which pod or service produced it. Splunk's search/dashboarding also lets me build saved searches or alerts for specific error patterns — e.g., alerting if a specific downstream-call failure pattern spikes, which is exactly the kind of signal that would have surfaced the mainframe-slowness incident I described earlier before it became customer-visible.
  - Metrics, APM, and distributed tracing — Datadog. This is where I get the aggregate, real-time operational view: request rate, error rate, and latency percentiles (p50/p95/p99) per service and per endpoint, via Datadog's APM integration with Spring Boot (typically the Datadog Java agent auto-instrumenting the app, plus Micrometer metrics exported to Datadog). Datadog APM also gives me distributed tracing — a visual timeline/flame graph of a single request as it moves across services, showing exactly where time was spent in the call chain. Going back to the resilience-pattern incident, this is exactly the tool that would show 'this request spent 4 of its 5 seconds waiting on the mainframe integration call specifically' — Datadog's trace view ties directly to the correlation/trace ID as well, so I can pivot from 'this trace looks slow in Datadog' to 'pull the full logs for this same correlation ID in Splunk' and get the complete picture, log detail plus timing visualization, for the same request.
  - Dashboards and alerting — Datadog is also where I'd set up service-level dashboards (error rate, latency, circuit-breaker state/open-rate if that's exported as a custom metric, saturation on thread pools) and alert thresholds, so the team gets paged on a real degradation — like error rate crossing a threshold or p99 latency spiking — rather than only finding out about an issue from a rep complaint or from manually digging through Splunk after the fact.
  - How this ties together in practice, using the earlier mainframe-slowness incident: a Datadog alert on rising latency/error rate for the mainframe-integration call would likely fire first, giving early warning something was degrading. From there, Datadog APM's trace view would show exactly which downstream call was the bottleneck. And Splunk would be where I'd pull the detailed logs for affected requests — via correlation ID — to confirm the circuit breaker correctly tripped and fallback responses were served as intended, rather than requests silently failing. Datadog tells you that and roughly where something's wrong quickly via metrics/traces; Splunk is where you go for the detailed forensic log trail once you know where to look.
  - One practical thing I enforce as a lead, regardless of which specific tools are in use: log level discipline — INFO for meaningful business events, WARN for recoverable/expected issues like a retry or circuit-breaker trip, ERROR reserved for genuine unexpected failures — because if every service logs excessively at INFO, Splunk ingestion volume and cost balloon, and the signal gets buried in noise exactly when you need to find it fastest during an incident."**
  - Likely follow-up to have ready: "How do you handle correlation IDs across the async/event-driven parts — Kafka messages, the S3-to-Lambda flow?" — same answer as before: the correlation/batch ID needs to be carried in the message payload or Kafka headers, not just HTTP headers, and both the Lambda logs and any Kafka-consuming service's logs need to tag that same ID so a single bulk-registration batch can be traced end-to-end across the async boundary in Splunk, even though it's not one continuous HTTP call chain
- Versioning and backward compatibility when multiple services evolve independently.
  - With eligibility, offer management, reward issuance, and the auth server all evolving independently — each with their own release cadence and team — the core risk is that a change to one service silently breaks a consumer that hasn't been updated yet. My general philosophy is: favor backward-compatible, additive changes as the default, and treat breaking changes as the exception that needs a deliberate versioning strategy, not the norm.
  - For REST APIs between services (and to the Angular frontend):
    - Additive-only changes preferred — adding a new optional field to a response, adding a new endpoint, adding a new optional request parameter with a sensible default — these don't break existing consumers, since a consumer ignoring a field it doesn't know about is the normal, expected behavior of a well-behaved client. This covers the large majority of real-world API evolution if you plan for it — most changes genuinely can be additive if you think ahead rather than reactively bolting on a breaking change.
    - Never repurpose or remove a field without a transition period — if a field's meaning needs to change, or it needs to be removed, that requires either a new field alongside the old one (with the old one deprecated and eventually removed after consumers have migrated) or a genuine version bump — never silently changing what an existing field means, since that's the kind of break that doesn't fail loudly, it just produces wrong data silently, which is worse than a hard failure.
    - When a genuine breaking change is unavoidable, I use URI versioning (/api/v1/offers, /api/v2/offers) as the default choice — it's explicit, easy to route, easy to run both versions simultaneously during a transition, and easy to see in Splunk/Datadog logs and dashboards exactly which version is being called and by whom, which matters for knowing when it's actually safe to retire the old version. I'd run v1 and v2 in parallel, monitor v1's traffic in Datadog to see when it's dropped to near-zero (confirming all real consumers have migrated), and only then deprecate/remove it — not on a calendar date, but on actual usage evidence.
  - For Kafka events specifically, this needs its own thinking since event consumers can be more numerous and less visible than direct API callers — you often don't know every consumer of a topic the way you know every caller of a REST endpoint. I'd use a schema registry (Avro or Protobuf with Schema Registry) rather than loose JSON, specifically because it enforces schema compatibility rules at publish time — you configure the registry for backward-compatible evolution (new optional fields with defaults are fine; removing or renaming a field, or changing a type, gets rejected at publish time before it can break every downstream consumer silently). That's a much stronger guarantee than REST versioning gives you, because with REST a consumer chooses when to call a new version, but with Kafka, once an event's shape changes, every consumer sees it on their next poll whether they're ready or not — so enforcing compatibility rules at the schema level, not just by convention, is genuinely important here, not optional.
    - Contract testing — for both REST and event contracts, I'd want consumer-driven contract tests (Pact is the common tool) in CI, where a consuming service defines the contract it expects from a producer, and that contract is verified against the producer's actual API/schema before either side deploys. This catches a breaking change before it reaches production — a producer's CI pipeline fails if it would break a known consumer's contract — rather than discovering the break only after both sides have deployed independently and something starts failing in production. This matters a lot in an org where different teams own different services and don't necessarily coordinate every release closely.
    - Coordinating actual rollout, practically: even with backward-compatible API design, I still want visibility into who's calling what version — that's where Datadog's service-level dashboards and Splunk's request logs come in again: tagging requests by API version (or by consumer service identity) lets me see real usage patterns, confirm a new version is being adopted as expected, and confirm an old version's traffic has genuinely dropped to zero before we decommission it, rather than guessing or relying on teams to proactively tell us they've migrated.
  - Where I apply extra caution, specific to this platform: reward issuance and anything touching financial correctness gets the most conservative versioning discipline — I'd rather maintain an old version longer than necessary and eat some maintenance overhead, than risk a subtly-breaking change reaching a consumer that hasn't updated, given the cost of that going wrong. For something lower-stakes like an internal reporting/dashboard consumer, I'd be more willing to move faster and coordinate a direct migration conversation with that one team rather than maintaining parallel versions indefinitely."**
  - Likely follow-up to have ready: "How do you handle a consumer that never migrates off an old version?" — good answer: that becomes a real conversation, not just a technical problem — Datadog usage data gives you the evidence to have that conversation (showing exactly which team/service is still calling the deprecated version and how often), and as a lead I'd escalate it as an organizational/prioritization issue with that team's lead rather than letting an old version linger indefinitely just because nobody wants to have the conversation — indefinite dual-maintenance is itself a real cost and risk
- How do you handle configuration and secrets management at scale across many services?
  - I treat configuration and secrets as two related but distinctly handled concerns — configuration is fine to be visible and version-controlled; secrets should never be, at any point, even in a deployment manifest.
    - Configuration (non-sensitive): this is what Spring Cloud Config Server handles, as we discussed — centralized, Git-backed, environment-scoped configuration for things like service URLs, timeouts, feature flags, retry/circuit-breaker thresholds. This is safe to version-control and review through normal PR process, since there's nothing sensitive in it, and having it in Git gives us full change history and easy rollback if a config change causes an issue.
    - Secrets — a fundamentally different handling path. Anything sensitive — database credentials, the OAuth client secret for our Spring Boot auth server, API keys for third-party integrations, AWS credentials where IRSA doesn't already cover it — never goes into Config Server, never goes into a Git-tracked YAML file, and never gets baked into a container image or an environment variable value directly. Instead, we use a Secret Manager as the actual store of truth for those values, and our deployment config — the pike manifest we discussed for the Angular app, and the equivalent for backend services — references the path to the secret in Secret Manager, not the secret value itself. That distinction matters a lot: the deployment YAML, which does go through normal code review and lives in a repo, is completely safe to look at even though it configures which secrets a service needs, because it only ever contains a pointer/path, never the actual credential.
  - How that resolves at runtime: the service (or the platform layer handling deployment) fetches the actual secret value from Secret Manager at deploy/startup time, injected into the running container — typically as an environment variable populated just-in-time, or mounted as a file the app reads on startup — rather than that value existing anywhere in source control, CI logs, or a Docker image layer. Combined with IRSA, which we discussed for the S3/file-registration bucket access, the pod's identity itself determines what it's allowed to fetch from Secret Manager — least-privilege applied consistently: a service can only read the specific secrets it's been explicitly granted access to, not every secret in the account.
  - Why this separation matters at scale, with the number of services we've discussed: if secrets were scattered across each service's own environment-variable configuration or, worse, checked into each service's config repo, that's both a security risk (secrets sprawled across many places, hard to audit, hard to rotate) and an operational one (rotating a shared secret means finding and updating it in every place it was duplicated). With a central Secret Manager and services referencing it by path, rotating a credential is a one-place operation, and access can be audited centrally — I can see exactly which services/roles have access to which secrets, which matters a lot in a regulated environment like this one where access auditing is a real compliance requirement, not just a nice-to-have.
  - Secret rotation, specifically — I'd want services to support picking up a rotated secret without requiring a full redeploy where possible, since a credential that requires a service restart to rotate tends to make people rotate less often than they should, purely out of operational friction. Whether that's practical depends on the specific secret and how it's consumed (a database connection pool can sometimes pick up rotated credentials on next connection attempt; some secrets genuinely do require a restart) — but I'd flag that as a design consideration when setting up a new service's secret dependencies, not something to figure out after the first rotation incident.
  - What I actively review for, as a lead, when someone adds a new service or a new dependency: making sure nobody's tempted to shortcut this by putting a secret directly into an environment variable value in the deployment YAML 'just for now' — that's exactly the kind of thing that gets forgotten and left in place, and once a secret has touched a Git-tracked file even briefly, it needs to be treated as compromised and rotated, since Git history doesn't forget. I'd rather that friction exist upfront — going through Secret Manager properly from day one — than deal with a rotation-after-the-fact cleanup later."**
  - Likely follow-up to have ready: "How do you handle secrets needed locally by a developer for local development, without them needing broad Secret Manager access?" — reasonable answer: local dev typically uses separate, low-privilege dev/sandbox credentials (never real prod secrets), often provisioned through a scoped-down Secret Manager path or a local .env file that's gitignored and documented as dev-only, explicitly never the same credentials or access level used in production
- How do you switch configuration between environments at runtime (Spring profiles, `application-{profile}.yml`, environment variables)?
  - We use a layered approach — Spring profiles as the mechanism, Config Server as the source of truth, and Kubernetes/pike as what actually decides which profile is active per environment.
  - Spring profiles as the core mechanism: each service has profile-specific configuration — application.yml for defaults/common config, and application-{profile}.yml for environment-specific overrides (application-dev.yml, application-qa.yml, application-uat.yml, application-prod.yml). Spring Boot merges the base config with whichever profile-specific file matches the active profile, so environment-specific values (a downstream service URL, a feature flag, logging verbosity) override the defaults only where they need to differ.
  - But we don't rely on bundling all those profile files into the deployed artifact — that's where Spring Cloud Config Server comes back in, as we discussed. Rather than each service carrying every environment's config baked into its own jar, Config Server centrally stores the profile-specific configuration (Git-backed), and the service pulls the config matching its active profile from Config Server at startup. That keeps the actual deployable artifact environment-agnostic — the exact same built jar is promoted from dev through prod, and it's purely the active profile (and what Config Server serves for that profile) that determines its behavior per environment, which ties back to the same principle I mentioned for the Angular app — build once, configure per environment, rather than rebuilding per environment.
  - How the active profile actually gets set at runtime: via the SPRING_PROFILES_ACTIVE environment variable, set as part of the Kubernetes deployment manifest for that environment — so it's the pike-style deployment config (the same pattern we discussed for the Angular app's environment vars) that tells a given pod 'you are running as the QA instance,' by setting SPRING_PROFILES_ACTIVE=qa. That single environment variable is really the pivot point — everything else (which Config Server profile gets pulled, which application-{profile}.yml overrides apply) cascades from that one value being different per environment/namespace.
  - Where plain environment variables come in, versus Config Server-managed YAML: I distinguish between configuration that's genuinely deployment/infrastructure-specific — things that differ because of where the pod happens to run, like proxy settings, or a pod-specific resource limit — versus configuration that's genuinely business/application-level, like a retry threshold or a feature flag. The former tends to live as plain Kubernetes-injected environment variables directly in the deployment manifest (as we saw in the pike config for the Angular app — proxy settings, host names). The latter — application behavior config — I prefer to live in Config Server rather than as scattered environment variables in the deployment YAML, because Config Server gives me versioning, easy diffing between environments, and the ability to push a config change and trigger a refresh (via /actuator/refresh or Spring Cloud Bus) without necessarily needing a full redeploy, which a plain environment variable change wouldn't give me — changing an env var in the deployment manifest still requires a pod restart to take effect.
  - Secrets, tying back to the previous question, don't go into application-{profile}.yml at all, even the profile-specific ones — they're injected as environment variables at deploy time from Secret Manager, referenced by path in the deployment config, exactly as we discussed. So the full picture per pod at startup is: SPRING_PROFILES_ACTIVE set by the deployment manifest tells the service which environment it is; non-sensitive config for that profile comes from Config Server; sensitive config comes from Secret Manager via environment variables injected by the platform; and truly infra-level values (proxy, resource-adjacent settings) are plain environment variables set directly in the deployment manifest. Each of those four falls into a distinct, deliberate bucket rather than everything being lumped into one undifferentiated 'config' blob.
  - Why I keep these buckets deliberately separate, as a lead reviewing a new service's config setup: mixing them — e.g., putting a business feature flag directly as a raw Kubernetes env var instead of in Config Server, or worse, putting a secret into application-prod.yml — tends to happen when someone's moving fast and just wants something to work, but it erodes exactly the benefits (auditability, easy rotation, easy environment diffing) that the layered setup is there to provide. I'd catch that in review and push it back to the right bucket rather than letting a shortcut become the pattern other engineers copy."**
  - Likely follow-up to have ready: "What happens if SPRING_PROFILES_ACTIVE is accidentally left unset, or set wrong, for a deployment?" — good answer: I'd want a fail-safe default profile that's intentionally not production-like (e.g., defaulting to something that fails fast or clearly logs a warning) rather than silently defaulting to a permissive/prod-like config, so a misconfiguration is loud and obvious rather than silently running with wrong settings — that's a real production-safety consideration I'd bake into the base application.yml's defaults.
- If two microservices need the same piece of data, how do you avoid tight coupling between them (data duplication with events, API composition, BFF pattern)?
  - This comes up constantly once you've split into services with the boundaries we discussed earlier — eligibility, offer management, and reward issuance all care about 'offer' data in some form, so the question of how they share that without becoming tightly coupled is a real, recurring design decision, not a one-time thing.
  - First principle: one service owns the data, others consume it through an API — never shared direct database access. Whichever service is the actual source of truth for a piece of data (offer management owns offer definitions, for instance) exposes it through a well-defined API contract; other services that need that data call that API rather than reading the owning service's database directly. Two services reading/writing the same tables is the single most common way microservices end up tightly coupled in practice — it means a schema change in one service silently breaks another, and it defeats the whole point of splitting into independently deployable services in the first place. I treat 'no shared database' as close to a hard rule, not a preference.
  - For read-heavy dependencies, a few patterns depending on the freshness/coupling trade-off needed:
  - Direct synchronous API call — simplest, always returns current data, but couples the caller's availability to the owning service's availability (which is exactly why the resilience patterns — timeouts, circuit breakers, fallbacks — we discussed earlier matter here specifically). I'd use this when the calling service genuinely needs guaranteed-fresh data and can tolerate the coupling, or has good fallback behavior when the dependency is degraded.
  - Event-driven data replication (each service maintains its own local, denormalized copy) — the owning service publishes events (via Kafka, using the outbox pattern we discussed to guarantee reliable publishing) whenever the data changes, and consuming services maintain their own local read-optimized copy of just the fields they actually need, kept in sync by consuming those events. This is what I'd favor when a service needs that data very frequently, needs low-latency access, and can tolerate some eventual-consistency lag — exactly the trade-off I described earlier for eligibility being okay with slightly-stale data. The real win here is decoupling: eligibility can keep functioning even if offer-management is temporarily down, since it's reading its own local copy, not making a live call.
  - API composition / aggregation at a higher layer — if a specific consumer (like the Angular app, or a BFF layer) needs data assembled from multiple services for one screen, rather than each service reaching into another, I'd have that composition happen at the edge — either the frontend making multiple calls and combining them, or a dedicated aggregation/BFF service doing that composition — rather than baking cross-service knowledge into the core domain services themselves.
  - Which pattern I pick, concretely: for eligibility needing offer-definition data at high frequency, low-latency, in a way where staleness is acceptable — that's the event-driven local-copy pattern. For something less frequent, more transactional, where staleness genuinely isn't acceptable — like reward issuance needing to confirm current eligibility right before issuing a reward — that's a direct synchronous call, deliberately, protected by the resilience patterns we discussed, because in that specific case correctness matters more than decoupling.
  - A subtler form of coupling I actively watch for, beyond just 'don't share a database': API contract coupling. Even with a clean API boundary, if consuming services depend on very specific, unstable details of another service's response shape, that's still tight coupling — just moved up one layer. This is exactly why the DTO-contract and backward-compatibility discipline we talked about earlier matters here too: a stable, deliberately-versioned API contract is what actually keeps services loosely coupled in practice, not just the existence of an API boundary on paper.
  - And the organizational form of coupling — Conway's Law again — if two services need the same data constantly and the interaction is genuinely tight and synchronous, that's sometimes a signal the boundary itself might be drawn wrong, going back to the service-boundary discussion; not every case of 'these two need the same data' should be solved with more integration plumbing — sometimes it's a signal to reconsider whether those two things should actually be one service, or that the data genuinely belongs to a third, more shared context neither currently owns cleanly.**
  - In short: ownership is unambiguous, data crosses boundaries only through APIs or events, never a shared database, and I choose between synchronous calls and event-driven local copies based on how much staleness a specific consumer can actually tolerate — not defaulting to one pattern everywhere just because it was the first one implemented."
  - Likely follow-up to have ready: "How do you keep an event-driven local copy from silently drifting out of sync with the source of truth over time?" — good answer: periodic reconciliation jobs that compare the local copy against the source (or against a checksum/version the source publishes) and alert or self-heal on drift, since event-driven sync can occasionally miss an event (a consumer was down during a publish, a bug in the consumer) and you don't want that discovered only when a customer-facing inconsistency surfaces — this ties back to the monitoring/alerting discussion via Datadog

## Monolith → Microservices Migration

- Walk me through a real migration you led — what triggered it, how did you prioritize which modules to peel off first?
  - The offers platform I worked on was originally entirely on mainframe — offer definitions, eligibility rules, and reward processing all lived in COBOL-based batch and transaction processing systems. I led the effort to migrate that into a modern microservices architecture running on Spring Boot and AWS.
  - What triggered it: A few converging pressures, which is usually how these decisions get made — it's rarely one single reason.
    - Change velocity — any new offer type or business rule change required a mainframe development cycle, which was slow and required specialized COBOL skills that were increasingly hard to staff. The business wanted to launch and iterate on offers/promotions much faster than the mainframe release cycle allowed.
    - Real-time requirements — a lot of mainframe processing was batch-oriented, but the business increasingly wanted real-time offer eligibility checks and reward issuance — a rep or a customer-facing system needing an immediate answer, not waiting for an overnight batch job.
    - Integration friction — connecting the mainframe to newer systems (web/mobile channels, the rep tools like the one I built) required brittle point-to-point integrations, often through file transfers or older middleware, which made every new integration project slow and risky.
    - Cost and talent risk — mainframe capacity and specialized mainframe engineering talent are both expensive and shrinking resources industry-wide; leadership wanted to reduce that long-term dependency.
  - How I prioritized which capability to peel off first: 
    - I didn't start with the most complex piece, and I didn't start with the riskiest piece — I looked for the capability that was simultaneously high business value to modernize, and lowest risk to extract first, specifically favoring something closer to the edge of the system rather than something deeply entangled with core transaction processing.
    - Concretely, that meant starting with offer eligibility/lookup — a largely read-oriented capability: given a customer/account, what offers are they eligible for. That was a good first candidate because:
    - It was read-heavy and closer to stateless — lower risk than migrating something that writes/mutates core account or reward-issuance data, where a bug has real financial consequences.
    - It had a clear, well-understood contract — the business rules for eligibility were reasonably well documented, versus some of the older reward-calculation logic where institutional knowledge had eroded over the mainframe's decades of life, and where I wanted more time to properly reverse-engineer the logic before touching it.
    - It unlocked real, visible value quickly — once eligibility checks were exposed as a fast REST API instead of a mainframe round-trip, that immediately benefited multiple consuming systems, which built momentum and stakeholder confidence in the migration approach before we touched anything higher-risk.
    - We used a Strangler Fig approach for the transition — rather than a big-bang cutover, the new eligibility microservice sat alongside the mainframe, and we routed traffic to it incrementally, starting with lower-risk internal consumers (like reporting or internal tools) before routing real customer-facing/transactional traffic to it, and kept the mainframe as the fallback/source of truth until we'd built confidence in the new service's correctness through parallel-running and comparing results.
    - The genuinely hard part specific to mainframe (versus a monolith-to-microservices migration) was data access and synchronization — the mainframe's data lived in formats like VSAM/DB2 that aren't naturally consumed by modern services, so we had to build a data-replication layer (CDC-style, or scheduled extracts depending on the specific data source's capabilities) to get eligibility-relevant data into a modern database the new service could query directly, while the mainframe remained the system of record during the transition. That meant real engineering effort just on the data pipeline before the actual business logic migration could even start — something I'd flag as a distinct workstream, not an afterthought, when leading a mainframe migration specifically.
    - After eligibility, we moved to offer management/administration — which is actually where the rep-facing tool I described earlier came in; once offer data itself had a modern service and database behind it instead of the mainframe, building a modern Angular/Spring Boot admin tool for reps to create and manage offers became possible, whereas before that would have meant building a UI on top of mainframe transactions directly, which nobody wanted to do.**
    - Reward issuance and the more transactional, financially-consequential pieces came later — deliberately, since that's where the risk of getting it wrong was highest, and by that point we had a proven pattern, a working data-sync approach, and organizational trust built from the earlier, lower-risk wins.**
    - What I'd do differently, if asked: I'd invest earlier in build automated parallel-run comparison tooling — systematically comparing the new service's output against the mainframe's for the same inputs over an extended period before fully cutting over — rather than relying mostly on manual QA and a shorter validation window for the first migrated capability. That's a lesson that paid off on later migrations in the sequence but cost us some extra manual validation time on the first one."**
  - Likely follow-ups to have ready:
    How did you handle the mainframe team's involvement — were they resistant, threatened by this?" — good honest answer, if it applies: mainframe engineers often have deep, hard-to-replace institutional knowledge of business rules that were never fully documented elsewhere — involving them early as domain experts (not just as people being replaced) both de-risked the migration and helped with change management.
    How long did the eligibility service migration take, end to end?" — have a rough, honest timeframe ready even if approximate — interviewers often want a sense of real-world scale, not precision
